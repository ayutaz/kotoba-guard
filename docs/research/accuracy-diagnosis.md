# 開発用精度評価の診断

後続の完了記録: M1の[採点感度](scoring-sensitivity.md)に加え、`d9c44d6`で[全confidence閾値状態](confidence-frontier.md)も診断した。全4モデルで目標同時達成0点、参照の最大Recall66.89%。下記の当初計画にある粗い閾値間の追加走査は完了しており、同じcacheで繰り返さない。製品閾値・独立gold未確保・元モデル精度未達の判断は維持する。

2026-11-27 に保存された開発用評価を、採点コードと固定プロトコルの実装に照らして確認した。対象は `artifacts/corpus-evaluation/development-v1/evaluation.json` と `decision.json` で、学習データから選んだ開発用サブセットである。これは閾値を決めるための校正資料であり、独立した一般精度の証拠ではない。held-out の結果は閾値選択に使用していない。

## 結論

現時点で最も大きい問題は、モデルの実用精度が開発用データでも受け入れ目標に届いていないことだ。QUInt8 の閾値 0.5 では labeled event の Precision 78.18%、Recall 62.80%、F1 0.6965、正常文の誤検出は 1,000 件中 55 件（5.5%）だった。開発用に試した全閾値で、Precision 95%、Recall 80%、正常文誤検出率 2% 以下を同時に満たす点はなかった。`decision.json` が `admissible: false` のまま 0.5 を診断用に保持している判断は、保存済み結果と一致する。

PyTorch reference も閾値 0.5 で Precision 79.38%、Recall 65.24%、F1 0.7162、正常文誤検出 5.5% であり、基準モデル自体が目標未達である。したがって、QUInt8 の悪化だけを修正しても製品目標を達成できる根拠はない。QUInt8 は開発用 F1 が reference より 0.01965 低く、量子化の影響も別途残っている。

## 閾値の挙動

下表は開発用評価の QUInt8 結果である。正常文誤検出は、少なくとも1件の検出を受けた正常レコード数であり、トークン単位の誤検出率ではない。

| 閾値 | Precision | Recall |     F1 |    正常文誤検出 |
| ---: | --------: | -----: | -----: | --------------: |
| 0.50 |    78.18% | 62.80% | 0.6965 | 55/1,000 (5.5%) |
| 0.60 |    80.56% | 59.30% | 0.6831 | 40/1,000 (4.0%) |
| 0.70 |    81.95% | 53.94% | 0.6506 | 31/1,000 (3.1%) |
| 0.80 |    83.30% | 47.61% | 0.6059 | 18/1,000 (1.8%) |
| 0.90 |    83.49% | 33.98% | 0.4830 | 10/1,000 (1.0%) |
| 0.95 |    84.41% | 24.25% | 0.3767 |  1/1,000 (0.1%) |
| 0.99 |    70.27% |  5.06% | 0.0945 |  0/1,000 (0.0%) |

閾値を上げると正常文誤検出は減るが、Recall が急落する。0.8 は誤検出率の目標だけを満たし、Precision も Recall も製品目標を満たさない。Kotoba Guard の既定値0.5は upstream が定義した確率閾値ではない。公式推論例は softmax 確率の閾値を使わず、argmax が `OK` 以外のトークンを出力する。Kotoba Guard の閾値は製品ポリシーであり、確率校正の結果として扱わない。

## ラベル別の弱点

閾値 0.5 の QUInt8 ラベル別結果は次の通り。サポート数は gold の件数で、希少なラベルの数値は大きく変動しやすい。

| ラベル             | サポート | Precision | Recall |     F1 |
| ------------------ | -------: | --------: | -----: | -----: |
| deletion           |      205 |    83.43% | 68.78% | 0.7540 |
| insertion_a        |      173 |    82.58% | 73.99% | 0.7805 |
| insertion_b        |       41 |    76.92% | 73.17% | 0.7500 |
| kanji-conversion_a |      377 |    75.56% | 62.33% | 0.6831 |
| kanji-conversion_b |       38 |    52.94% | 23.68% | 0.3273 |
| substitution       |      142 |    74.55% | 57.75% | 0.6508 |
| transposition      |        9 |    85.71% | 66.67% | 0.7500 |
| others             |       42 |    82.35% | 33.33% | 0.4746 |

主な弱点は `kanji-conversion_b` の低い Recall と Precision、`others` の低い Recall、`substitution` と `kanji-conversion_a` の取りこぼしである。`transposition` の F1 は高く見えるが、gold サポートが9件しかないため、他のラベルとの単純比較は避ける。これはラベル定義の推測ではなく、固定 config の label mapping に基づく集計である。

## 採点実装の確認

ラベルIDは `config.json` の `id2label` と `label2id` を読み、整合性を検査している。公式 README の推論処理と同じく、特殊トークンをoffsetで除外し、argmax の `OK` 以外を検出対象にしている。この部分にラベル順を推測している不備は見つからなかった。

採点側には、精度の解釈に影響するプロトコル上の注意がある。

1. `spans_from_logits` は logits を softmax に変換し、最大ラベルの confidence を閾値判定した後、隣接する同一ラベルのトークンを1 spanへ結合する。公式例はこの結合を行わない。したがって、閾値0.0でも公式のtoken出力と製品向けspan出力は同じ単位ではない。隣接トークンの結合は製品仕様としては合理的だが、公式結果との直接比較には不向きである。
2. 主指標の `containment_scores` は、予測spanがgold spanを含めば一致とする一対一マッチングである。開発用 QUInt8 の閾値0.5では labeled event F1 0.6965 に対し、厳密な raw span F1 は0.4035、token-projected span F1は0.5445だった。event指標を唯一の精度と解釈せず、厳密spanとtoken指標を併記する必要がある。
3. 75件の文書に複数の完全なdiff再構成があり、現在のプロトコルは予測との containment 一致数が最大になる再構成を主指標ごとに選ぶ。これは固定プロトコルに明記された選択であり、偶然の実装バグではないが、予測を使ってgoldの解釈を選ぶため、最良寄りのスコアになる可能性がある。canonical固定、全候補の最悪値、候補間の幅を追加する感度分析が必要である。
4. zero-width gold event は129件あり、tokenへの投影にはプロジェクト固有の包含規則がある。これは upstream の公式評価方法ではなく、脱字をtoken分類へ写像するための採点規則である。投影不能文書は0件だった。

したがって、現時点で「採点コードがラベルを取り違えている」と判断する根拠はない。一方、containmentによる主指標と曖昧diffの予測依存選択は、実用精度を楽観的に見せうるプロトコル上の制約として明記すべきである。

## 変換・量子化との切り分け

保存済み parity は、FP32 ONNX が通常token 62,936件で argmax 100%、最大logit差約4.0e-5、FP16 が argmax 100%、最大logit差約2.77e-2だった。これらは採点実装ではなく変換経路の数値差であり、FP32の変換はこの評価範囲で reference と一致している。

QUInt8 は argmax 一致99.7887%でも最大logit差約5.78、平均差約0.425で、開発用 event F1 の低下と一致する。argmax一致率だけでは閾値判定やspan結合の差を保証できない。量子化の改善は、精度目標未達の根本解決とは分けて扱う必要がある。

## 次に行う最小実験

1. **採点感度だけを追加測定する。** 既存logits cacheを再利用し、canonical固定、最良候補、最悪候補の3通りを同じ閾値で集計する。新しい推論やheld-outの参照は不要で、曖昧diff 75件が結論に与える幅を確認できる。
2. **開発用だけで閾値曲線を細かくする。** 0.01刻みではなく、予測confidenceの分位点または全候補を使い、Precision/Recall/正常文誤検出のPareto曲線を作る。選択条件は開発用に固定し、held-outを見て閾値を変更しない。
3. **ラベル別の校正を測る。** とくに `kanji-conversion_b` と `others` について、confidence分位点、予測数、誤検出率を分けて確認する。softmax値を確率として再命名せず、必要なら開発用データ内で校正方法を比較する。
4. **QUInt8の変換差を別ゲートで調べる。** embeddingを含む量子化とMatMulのみの比較、ラベル別logit差、CPUとbrowser runtimeの差を固定入力で比較する。量子化のF1差を1ポイント以内にすることと、reference自体のPrecision/Recallを上げることを混同しない。

次の実験が完了するまで、0.5を「推奨精度」と表示せず、診断用の固定閾値として扱う。開発用の結果だけで日常文・メール・SNSへの一般化や、false positive 2%以下を主張してはいけない。
